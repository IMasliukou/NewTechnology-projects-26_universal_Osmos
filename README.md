# NewTechnology-projects-26_universal_Osmos

Единый рабочий процесс проектирования **электрических схем в KiCad** для проектов
заказчика **ModernTechnologies**.

Цель репозитория — чтобы у всех был **один подход**: схемы хранятся в git,
проверяются и экспортируются одинаково, а результаты (PDF/SVG/нетлист/BOM) всегда
воспроизводимы и доступны для ревью.

## Область применения (важно)

Это проекты **автоматизации**: нас интересует **только схема** (электрика —
цепи управления и силовые), **печатных плат (PCB) нет**. Поэтому в подходе:

- работаем только со схемой (`.kicad_sch`), файлов платы (`.kicad_pcb`) нет;
- **футпринты/посадочные места не нужны**, гербер/DRC не делаем;
- вместо этого важны: **нетлист** (перечень соединений/проводов), **BOM**
  (перечень аппаратов: реле, автоматы, клеммы, датчики) и **ERC** (проверка связей);
- набор символов — «электротехнический» (реле, контакторы, выключатели, двигатели,
  датчики, клеммники), см. [`lib/README.md`](lib/README.md).

---

## Почему «где результаты?» — и как это решается

Cloud-агент работает во **временной виртуальной машине**. Всё, что нарисовано в
GUI KiCad, но **не закоммичено в git**, исчезает вместе с машиной. Именно поэтому
предыдущая работа «настраивалась, но результатов не видно».

Решение — **schematic-as-source**: файлы проекта KiCad (`.kicad_pro`,
`.kicad_sch`) лежат в репозитории. Они и есть результат. Картинки и отчёты
(PDF/SVG/PNG/нетлист/BOM/ERC) генерируются из них автоматически командой
`scripts/export.sh`.

## Структура репозитория

```
.
├── .cursor/environment.json        # окружение: ставит KiCad при старте агента
├── scripts/
│   ├── setup.sh                    # идемпотентная установка KiCad + библиотек
│   ├── export.sh                   # экспорт схем в PDF/SVG/нетлист/BOM/ERC
│   └── sync-standards.sh           # синхронизация правил из базы знаний стандартов
├── standards.sync.conf             # настройки источника стандартов (база знаний)
├── lib/                            # общие «электротехнические» символы ModernTechnologies
├── imports/                        # исходники для переноса (P-CAD / Altium / PDF)
├── templates/
│   └── project-template/           # шаблон нового проекта (титульный блок уже заполнен)
├── projects/
│   └── example-voltage-divider/    # демонстрационный пример (для проверки пайплайна)
└── output/                         # сгенерированные артефакты (не в git)
```

## Быстрый старт

### 1. Установить инструменты (один раз в новом окружении)

```bash
bash scripts/setup.sh
```

Ставит **KiCad 10.0.x** (текущий стабильный релиз из официального PPA `kicad/kicad-10.0-releases`,
как на Windows у инженеров), официальные библиотеки символов и `poppler-utils`, а также
инициализирует глобальные таблицы библиотек, чтобы `kicad-cli` мог делать ERC
без запуска GUI. В cloud-агенте это происходит автоматически через
`.cursor/environment.json`.

### 2. Открыть пример и проверить экспорт

```bash
scripts/export.sh projects/example-voltage-divider
ls output/example-voltage-divider/
# example-voltage-divider.pdf / .svg / .net / .bom.csv / .erc / .png
```

### 3. Создать новый проект

```bash
cp -r templates/project-template projects/my-new-board
cd projects/my-new-board
# переименуйте файлы под имя проекта:
for f in project-template.*; do mv "$f" "my-new-board.${f##*.}"; done
```

Дальше есть два способа рисовать — оба заканчиваются коммитом файлов в git.

> Переносите существующий проект из **P-CAD / Altium / PDF**? См. пошаговую
> инструкцию в [`imports/README.md`](imports/README.md) (какие форматы KiCad
> читает и как действовать по каждому источнику).

## Два способа рисовать схемы (единый результат)

### A. GUI (ручное рисование в KiCad / eeschema)

Так рисует инженер вручную. В cloud-агенте GUI запускается через
computer-use/VNC. **Главное правило:** после рисования обязательно
`git add / commit / push` — иначе результат потеряется.

```bash
eeschema projects/my-new-board/my-new-board.kicad_sch   # открыть редактор схем
```

### B. Headless / как код (для автоматизации и ревью)

Файл `.kicad_sch` — это текстовый s-expression формат, его можно
генерировать и хранить в git. Проверка и экспорт — без GUI:

```bash
scripts/export.sh projects/my-new-board
```

Пример `projects/example-voltage-divider` сделан именно так и полностью
воспроизводим.

## Проверка и артефакты для заказчика

`scripts/export.sh` для каждого проекта кладёт в `output/<project>/`:

| Файл | Назначение |
| --- | --- |
| `<project>.pdf` | схема для печати и передачи заказчику |
| `<project>.svg` | векторная схема (удобно для ревью и diff) |
| `<project>.net` | нетлист — **перечень соединений/проводов** |
| `<project>.bom.csv` | BOM — **перечень аппаратов** (сгруппирован по значению) |
| `<project>.erc` | отчёт ERC — **проверка связей** (KiCad 8+) |
| `<project>.png` | быстрый растровый предпросмотр |

Нетлист показывает, что схема соединена правильно (какие цепи есть, какие
выводы куда подключены). ERC (`kicad-cli sch erc`) автоматически находит типовые
ошибки: неподключённые выводы, «висящие» метки, питание без источника и т.д. —
всё без открытия GUI.

> Пример `example-voltage-divider` проходит ERC с **0 ошибок** (на KiCad 10.0.6 —
> 1 безобидное предупреждение `lib_symbol_mismatch`: кэш символа в схеме чуть
> отличается от библиотеки). Это самое частое и безобидное предупреждение KiCad;
> оно убирается в GUI через **Tools → Update Symbols from Library**.

## Версия KiCad — одна на всех (важно!)

Файл схемы, сохранённый в **более новой** версии KiCad, **не откроется в более
старой** (формат `.kicad_sch` меняется между мажорными версиями). Поэтому для
единого подхода все — и локально, и в облаке — используют **одну и ту же
стабильную** версию.

- В этом репозитории зафиксирован **стабильный KiCad 10.0.x** (`scripts/setup.sh`),
  как на Windows у инженеров (`Stable Release 10.0.6`).
- Ставьте локально тоже **стабильный** релиз KiCad 10 (не nightly).
- **Nightly/dev-сборки не используем.** Если KiCad показывает версию вида
  `10.99.x` или `X.99` — это ветка разработки (предрелиз), она нестабильна и
  несовместима по формату файлов. Для схем заказчика это не подходит.

Сменить версию (например, на предыдущую стабильную или nightly) можно одной
строкой — переменной `KICAD_PPA` в `scripts/setup.sh`:

```bash
KICAD_PPA=kicad/kicad-9.0-releases  bash scripts/setup.sh   # предыдущая стабильная
KICAD_PPA=kicad/kicad-10.0-nightly  bash scripts/setup.sh   # nightly (не для прод)
```

## Как организован общий workflow и окружение

### Окружение (почему НЕ нужно жать «Save»)

Окружение задано **прямо в репозитории** — файл `.cursor/environment.json`
(команда `install: bash scripts/setup.sh`). Это «repo-managed» окружение: оно
имеет **высший приоритет** и применяется автоматически ко всем новым
cloud-агентам на этой ветке/после мержа. **Ничего сохранять кнопкой «Save» не
нужно.**

Кнопка «Save» в панели окружения относится к **другому** способу — окружению,
которое хранится в дашборде (не в репозитории). Мы им намеренно не пользуемся,
потому что версионирование в git лучше: конфигурация едет вместе с кодом, видна
в PR и одинакова у всех. Поэтому предложение «Save» можно **игнорировать**.

### Стандарты заказчика — из общей базы знаний

Общие стандарты работы с проектами **ModernTechnologies** живут в **отдельном
репозитории — базе знаний** (папка `standards/`), которая эволюционирует. В этот
проект правила подтягиваются скриптом:

```bash
scripts/sync-standards.sh
```

- Источник задаётся в `standards.sync.conf` (`STANDARDS_REPO`, `STANDARDS_REF`,
  `STANDARDS_SRC`) — впишите git-URL базы знаний.
- Скрипт копирует правила (`*.mdc`) из базы знаний в `.cursor/rules/`, удаляет
  устаревшие (по манифесту `.cursor/rules/.standards-manifest`) и **не трогает**
  локальные правила проекта.
- После синка проверьте изменения и закоммитьте `.cursor/rules/` (и манифест).
- Локальный кэш базы знаний (`.standards-cache/`) в git не хранится.

> Правило `.cursor/rules/kicad-schematic-workflow.mdc` — стартовая версия
> стандарта KiCad. Когда перенесёте его в базу знаний, удалите локальную копию и
> дайте скрипту управлять им (единый источник истины).

### Рабочий цикл (одинаковый для всех)

1. **Старт агента** → `.cursor/environment.json` сам ставит KiCad 9 и библиотеки.
2. **Рисуем/правим схему** — GUI (`eeschema`) или перенос из `imports/`.
3. **Проверяем и экспортируем** — `scripts/export.sh projects/<имя>` (ERC + PDF/SVG/нетлист/BOM).
4. **Ревью** — по артефактам из `output/` (PDF/SVG) и отчёту ERC.
5. **Коммит исходников** `.kicad_*` в git, изменения идут через PR.
6. `output/` в git не храним — он всегда пересобирается из исходников.

## Локальная работа в Cursor Desktop (Windows)

Часть работы можно вести локально, без облака. В Cursor Desktop агент работает
**прямо в ваших файлах на ПК** — без пересылки файлов через git между вами и
агентом (git остаётся только для командной работы и истории).

### Разовая настройка
1. Установите **Git for Windows** (даёт `git` и терминал **Git Bash**) и **Cursor Desktop**.
2. Склонируйте репозиторий: в Cursor → *Clone repository*, либо `git clone <URL-репозитория>`.
3. Откройте папку в Cursor и переключитесь на нужную ветку
   (пока PR не смержен — `cursor/kicad-schematic-workflow-a68d`; после мержа — `main`).
4. Добавьте `kicad-cli` в `PATH` — папку `C:\Program Files\KiCad\10.0\bin`.
   Проверка в терминале: `kicad-cli version` → должно быть `10.0.6`.

### Что важно про скрипты на Windows
- `scripts/setup.sh` — **только для облака** (Linux/apt). На Windows KiCad вы ставите
  вручную (уже сделано, 10.0.6) — `setup.sh` не нужен.
- `scripts/export.sh` и `scripts/sync-standards.sh` — bash-скрипты; запускайте их в
  **Git Bash** (или выберите Git Bash терминалом в Cursor). PNG-превью пропустится,
  если нет `poppler` — это не критично, PDF/SVG/нетлист/BOM/ERC будут.
- `.cursor/environment.json` локально **не используется** (это конфиг только для
  облачных агентов). `.cursor/rules/` работает и локально — агент соблюдает правила.

### Ежедневный цикл локально
1. Рисуете в KiCad (`eeschema`), файлы в `projects/<имя>/`.
2. Проверка/экспорт: в GUI (`Inspect → Electrical Rules Checker`, `File → Plot`) или
   `bash scripts/export.sh projects/<имя>` в Git Bash.
3. Обновить правила из базы знаний: `bash scripts/sync-standards.sh`.
4. Коммит и пуш из Cursor (или `git`).

Репозиторий один и тот же локально и в облаке — меняется только то, где вы кликаете.

## Единые правила для проектов ModernTechnologies

1. Один проект = одна папка в `projects/<имя>/`.
2. В титульном блоке — `company = ModernTechnologies`, ревизия в поле `rev`.
3. Общие компоненты — в `lib/`, а не копируются в каждый проект.
4. Питание и «земля» — через символы `power:*` (`GND`, `+5V`, …) и глобальные метки.
5. Каждое изменение схемы завершается коммитом `.kicad_*` файлов в git.
6. Артефакты (`output/`) не коммитятся — они всегда пересобираются из исходников.
